# Playroom SEO Bot — инструкция владельцам

## Что сейчас можно тестировать

Контур `keyword → generation → Telegram review → approval → staging publish` можно тестировать на staging. Публикация в production защищена дополнительными SEO/security-предохранителями.

Рабочая таблица: [PlayroomNearby SEO Editor Pipeline](https://docs.google.com/spreadsheets/d/10QigScXswOt9QUns059V5PWqc29aOul74UwNoUGSeAM/edit)

Telegram-бот: [@playroom_nearby_bot](https://t.me/playroom_nearby_bot)

## Первый запуск review-группы

1. Добавьте `@playroom_nearby_bot` в общую Telegram-группу владельцев.
2. Пока сервис запущен, отправьте в группе:

   ```text
   /seo_chat_id@playroom_nearby_bot
   ```

3. Передайте техническому админу отрицательный `Chat ID`, который вернёт бот. Админ запишет его в `settings.telegram_chat_id`.
4. После привязки любой обычный участник этой группы получает одинаковые права на просмотр, согласование и отмену. Команды из лички и других групп блокируются.

## Как запустить новую статью

Сначала подготовьте очередь на листе `keywords`: заполните ключ, locale и остальные контентные поля, затем поставьте строке статус `ready`. Расположите строки в нужной очередности сверху вниз.

В review-группе отправьте команду без параметров:

```text
/generate
```

Бот возьмёт физически самую верхнюю строку со статусом `ready`, зарезервирует именно её и вернёт её `keyword_id`. Число в колонке `priority` при ручном запуске не учитывается: приоритет задаётся порядком строк. Ключ, язык и настройки контента берутся из выбранной строки; параметры после `/generate` запрещены. После генерации и QA в эту же группу придёт карточка статьи.

Одновременно в очереди допускается до трёх заявок (`settings.telegram_generation_queue_limit`). После заполнения очереди бот попросит дождаться ближайшей карточки.

Повторная доставка одной и той же Telegram-команды не создаёт дубль. После успешного ответа генератора выбранный keyword получает статус `used`, даже если QA статьи нашёл блокеры: материал всё равно остаётся на проверке. При технической ошибке генерации keyword переводится в `paused`, бот сообщает об этом в группу, а автоматического платного повтора нет.

## Как согласовать статью

Если статья готова, нажмите кнопку `Согласовать` или отправьте:

```text
/seo_approve ARTICLE-ID
```

Команду можно отправить ответом на карточку без `ARTICLE-ID`:

```text
/seo_approve
```

Если текст требует правок:

1. Для автоматического исправления нажмите `Исправить ИИ` или ответьте на карточку:

   ```text
   /seo_regenerate
   ```

   После команды можно дописать пожелание редактора. Бот сохранит тот же `article_id` и строку; старый текст будет заменён только после успешного ответа генератора.
2. Для ручного исправления перейдите по ссылке из карточки на строку листа `articles` и поправьте текст, мета-поля, источники или внутренние ссылки.
3. Вернитесь в Telegram и согласуйте статью. Бот перечитает актуальную строку и заново выполнит QA.

Для отмены обязательно укажите причину:

```text
/seo_cancel ARTICLE-ID причина отмены
```

Для проверки состояния:

```text
/seo_status ARTICLE-ID
```

Полная справка:

```text
/seo_help
```

## Важные правила редактора

- Не меняйте `article_id`, `keyword_id`, `content_hash`, `telegram_message_id`, `ghost_post_id` и системные даты.
- Для новой статьи подготовьте строку `keywords` со статусом `ready`, поставьте её на нужное место в очереди и используйте `/generate` без параметров. Не создавайте системные ID вручную.
- Не редактируйте лист `events`: это журнал аудита.
- Не переводите статью в `approved` вручную. Действительным считается только approval из Telegram, привязанный к hash текущего текста.
- После approval не меняйте публикуемые поля. Если текст изменился, бот остановит публикацию со статусом `conflict`; статью нужно вернуть на проверку и согласовать заново.
- Конкретные цены, часы работы, адреса, рейтинги и заявления “лучший” допустимы только с актуальными источниками.
- Если бот показывает QA blockers, исправьте перечисленные причины и повторите approval.

## Что передать заказчикам

Передайте владельцам только:

- приглашение в review-группу Telegram;
- ссылку на Google Sheet с правами редактора;
- эту инструкцию;
- имя человека, которому сообщать о технических ошибках.

Не передавайте владельцам API-ключи, service-account JSON, `.env.local`, SSH-доступ или Ghost Staff token. Эти данные нужны только техническому админу и серверу.

Распределение ответственности:

- владелец контента проверяет смысл, факты, источники, тональность и дату публикации;
- любой участник review-группы может согласовать или отменить материал;
- технический админ управляет интеграциями, group chat ID и предохранителями публикации;
- разработчик разбирает статусы `failed_*`, `conflict` и ошибки внешних API.

## Чек-лист приёмки

- Бот отвечает на `/seo_chat_id` в нужной группе.
- После привязки `/seo_help` показывает справку; рабочие команды из чужой группы получают отказ.
- `/generate` без параметров резервирует существующую верхнюю строку `keywords` со статусом `ready`; команда с аргументами получает отказ.
- Порядок строк определяет ручной приоритет независимо от значения колонки `priority`.
- Повторная доставка команды не создаёт дублирующую статью и не резервирует следующий keyword.
- Один `ready`-keyword превращается в одну строку `articles`, а после ответа генератора получает статус `used`, включая случай QA-блокеров.
- При технической ошибке генерации keyword получает `paused`, старое содержимое очереди не теряется и автоматического повтора нет.
- В Telegram приходит ровно одна карточка.
- Ручная правка в Sheet учитывается при approval.
- `/seo_approve` создаёт audit event и переводит статью в `approved`.
- `/seo_cancel ... причина` сохраняет причину и создаёт audit event.
- При контентном тесте без публикации Ghost не меняется: `DRY_RUN=true`, `ALLOW_GHOST_PUBLISH=false` или `publication_enabled=false`.
- При staging acceptance-тесте approval автоматически публикует материал, если все три staging-предохранителя явно включены.

## Перед реальным запуском

Для ручной генерации нужны `ALLOW_TELEGRAM_GENERATION=true` на сервере и `telegram_generation_enabled=true` в таблице. Плановый генератор отдельно управляется `generation_enabled` и может оставаться выключенным.

Для staging-публикации нужны три независимых разрешения: `DRY_RUN=false`, `ALLOW_GHOST_PUBLISH=true` и `publication_enabled=true`. Для production дополнительно обязательны `security_ready=true` и `technical_seo_ready=true`; их включает технический админ только после отдельного acceptance-теста.
